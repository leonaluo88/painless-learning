# 自我改进

## 八之二、自我改进：用户不满意时，不只改网页，还要判断要不要改 skill

用户在生成后提出不满意、要求修改或调试网页时，按下面的步骤处理。AI 自己在交付前检查时发现了规则没覆盖到的问题，也走同样的流程。

**在同一个对话里一直有效**：只要这个对话里调用过本 skill，用户之后提出的任何修改意见、不满、新偏好或新约束，都按本节处理，即使那条消息没有再带上本 skill 的名字或斜杠命令，也不管隔了多少轮、中间聊过别的什么。不要等用户再次点名 skill 才考虑写进 skill；也不要因为用户这次没提 skill，就只改网页、不做第 2 步的归因。上一轮提出的 skill 修改卡片用户还没保存时，新的建议要把上一轮的内容合并进来，并告诉用户只保存最新一张。

### 1. 先把当前网页改好
按用户的要求修改 course.json 和网页。

### 2. 归因：判断问题的适用范围

| 范围 | 典型例子 | 怎么处理 |
|---|---|---|
| **仅这门课** | 这门课老师的记号、某个知识点讲错了、用户对这门课有特别的偏好 | 只改网页，并写进 course.json 的 `course_notes`，以后更新这门课时一律遵守。不改 skill |
| **某一类学科或规格** | 公式晦涩、推导跳步（数理类）；代码题判分太死板（编程类）；仿真题太像原题（备考·扎实） | 提出 skill 迭代建议，把规则加在对应学科或规格的那一节 |
| **所有学科都会发生** | 知识点拆得太粗或太碎、逻辑主线太笼统、自测题太简单 | 提出 skill 迭代建议，把规则加在通用的那一节 |

判断时要回答两个问题：
- 问题出在 skill 的哪一条规则上？是规则缺失、写得含糊，还是规则本身没问题、只是这次没做到？只是没做到时，不改 skill。
- 拿一门别的学科（或另一种规格）套用现在的规则，会不会出同样的问题？要举一个具体的例子。

判断不了时，把两种可能和各自的理由说出来，让用户选。

### 3. 提出 skill 迭代建议（先问，不直接改）
在这一轮回复的最后写一段“skill 迭代建议”：问题是什么；判断的范围，以及为什么不是“仅这门课”；拟新增或修改的规则原文，写明放进哪一节；会不会影响其他学科或规格。然后让用户选：采纳 / 换一个范围采纳（例如只用于数理类）/ 不采纳。**没有得到确认，不改 skill。**

示例：用户说“公式晦涩难懂、知识点讲得不深”。判断：公式多的课都会碰到，论述类课程不会，所以范围是“数理类”。建议在“按学科调整 → 数学、统计、计量、物理”里加一条讲解细度约束（例如：推导中每一行只做一种变换并写出依据；新符号在同一步里解释；一个知识点里的新公式不超过一个），先问用户要不要加，确认后再写入。

### 4. 用户确认后，更新 skill
- 能写入 skill 所在的文件夹时（例如 `~/.agents/skills/painless-learning-web/`、`~/.workbuddy/skills/painless-learning-web/`，或用户的 GitHub 仓库），直接修改 SKILL.md 或 references 里对应的文件（通用硬性要求改 SKILL.md，细节改对应的 reference）。
- 写不进去时，给出可以直接粘贴的修改内容（位置 + 新文本），并提醒用户：其他 agent 里装的副本也要同步。
- 在 `references/rule-changelog.md` 末尾追加一条：日期、触发的问题、适用范围、改了哪里。
- 用新规则重新检查当前网页，确保已经符合。

### 5. 规则怎么写
- 要具体、能检验：写“每个公式下面必须……”“每个知识点不超过……”，不写“讲得更清楚一些”这样的空话。
- 放在最窄的合适范围里：能放进学科小节的，就不放进通用小节。
- 和已有规则重叠或冲突时，改写或合并旧规则，不在后面叠加一条新的。
- 能被检查的规则，同时加进“交付前检查”。
